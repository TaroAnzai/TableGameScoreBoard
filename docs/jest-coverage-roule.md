# Jest Coverage 運用方針

## 1. 目的

Jest の Coverage は、単純に数値を高くすることを目的とせず、重要な機能や条件分岐に対して十分なテストが存在するかを判断するための指標として利用する。

特に麻雀集計スマホアプリでは、以下のような処理の回帰を防止することを重視する。

- データの取得・作成・更新・削除
- 点数入力・確定
- APIエラー時の処理
- 削除確認や未保存離脱時のキャンセル
- VIEW / EDIT / OWNER などの権限制御
- Deep Link や削除後の画面遷移
- 空データ、0、同点などの境界条件

Coverage の数値だけを上げるためのテストは作成せず、実際の障害リスクが高い処理から優先してテストを追加する。

---

## 2. Coverage の各指標

Jest Coverage では、主に以下の4指標を確認する。

| 指標       | 内容                   | 運用上の意味                                                   |
| ---------- | ---------------------- | -------------------------------------------------------------- |
| Statements | 実行された文の割合     | コード全体がどの程度テストから実行されたか                     |
| Branches   | 条件分岐を通過した割合 | `if`、三項演算子、`switch` などの分岐がテストされているか      |
| Functions  | 実行された関数の割合   | イベントハンドラ、mutation、コールバックなどが実行されているか |
| Lines      | 実行された行の割合     | コード全体の実行範囲を把握する基本指標                         |

特に **Branches と Functions を重視する**。

Lines が高くても、エラー処理、キャンセル処理、権限制御などの分岐がテストされていなければ、十分なテストとは判断しない。

---

## 3. ファイル単位の Coverage 目標

すべてのファイルに同じ Coverage を要求せず、機能の重要度によって目標値を分ける。

### P0・重要画面・重要処理

以下を目標とする。

| 指標       |    目標 |
| ---------- | ------: |
| Statements | 80%以上 |
| Branches   | 70%以上 |
| Functions  | 75%以上 |
| Lines      | 80%以上 |

対象例：

- `app/table/[tableKey].tsx`
- `app/tournament/[tournamentKey].tsx`
- グループ管理の主要画面
- 点数入力・確定処理
- 削除処理
- 権限制御
- Deep Link・主要画面遷移

---

### 中核 Hooks・業務ロジック

画面から独立してテストしやすい Hooks や業務ロジックは、画面コンポーネントより高い Coverage を目標とする。

| 指標       |    目標 |
| ---------- | ------: |
| Statements | 85%以上 |
| Branches   | 75%以上 |
| Functions  | 80%以上 |
| Lines      | 85%以上 |

対象例：

- `src/hooks/useTables.ts`
- `src/hooks/useTournaments.ts`
- `src/hooks/useGroups.tsx`
- `src/storage/*`
- `src/api/*` の独自実装部分

Hooks については、正常系だけでなく以下を確認する。

- API取得成功
- API取得失敗
- 作成成功・失敗
- 更新成功・失敗
- 削除成功・失敗
- query invalidate
- キャッシュ更新
- 異常レスポンス

---

### 通常の UI コンポーネント

表示を中心とした一般的なコンポーネントについては、以下を目安とする。

| 指標       |    目標 |
| ---------- | ------: |
| Statements | 70%以上 |
| Branches   | 60%以上 |
| Functions  | 70%以上 |
| Lines      | 70%以上 |

ただし、重要な条件分岐を持つコンポーネントについては、この基準より Branch Coverage を優先する。

例えば、表示内容が権限、状態、スコア、データ有無によって変わるコンポーネントは、通常UIより高い Branch Coverage を目指す。

---

## 4. プロジェクト全体の Coverage 目標

まず以下をプロジェクト全体の第1目標とする。

| 指標       | 第1目標 |
| ---------- | ------: |
| Statements | 75%以上 |
| Branches   | 65%以上 |
| Functions  | 70%以上 |
| Lines      | 75%以上 |

その後、主要機能のテストが十分になった段階で、以下を将来的な目標とする。

| 指標       | 将来目標 |
| ---------- | -------: |
| Statements |  80%以上 |
| Branches   |  70%以上 |
| Functions  |  75%以上 |
| Lines      |  80%以上 |

プロジェクト全体の Coverage は最低水準を監視するための指標として利用する。

実際のテスト追加優先順位は、全体Coverageの数字ではなく、**重要ファイルごとの Coverage と未テスト処理の内容**を見て判断する。

---

## 5. 自動生成コードの扱い

APIクライアントなどの自動生成コードは、原則として Coverage 対象から除外する。

対象例：

```text
src/api/generated/
```

自動生成コードはアプリ独自の業務ロジックではなく、Coverage に含めるとプロジェクト全体の数値を大きく歪める可能性がある。

Jest の設定では、例えば以下のように除外する。

```js
coveragePathIgnorePatterns: [
  '/node_modules/',
  '/src/api/generated/',
],
```

ただし、Coverage の数字を上げる目的で任意のファイルを除外してはならない。

除外対象は、自動生成物など「アプリ側で直接テストする責任がないコード」に限定する。

---

## 6. テスト追加の優先順位

Coverage レポートを確認した場合、以下の順番でテスト追加を検討する。

### 優先順位1：主要機能の未テスト処理

まず、障害が発生した場合の影響が大きい処理を確認する。

例：

- 卓
- 大会
- グループ
- 点数
- 削除
- 保存
- 権限制御
- Deep Link
- 画面遷移

Coverage が比較的高くても、重要な処理が未テストであれば優先する。

---

### 優先順位2：Branch Coverage が低い重要ファイル

Branch Coverage が低い場合は、正常系しかテストされていない可能性が高い。

以下を追加する。

- APIエラー
- キャンセル
- 権限制御
- 空データ
- データ欠損
- 境界値
- 条件による表示切替

---

### 優先順位3：Functions Coverage が低い重要ファイル

Functions Coverage が低い場合は、イベントハンドラや処理関数が実行されていない可能性がある。

以下を確認する。

- `onPress`
- 保存処理
- 削除処理
- 更新処理
- mutation
- callback
- navigation
- エラー処理

---

### 優先順位4：大きな未実行領域

Lines / Statements の Coverage が低く、未実行行がまとまって存在する場合は、その処理内容を確認する。

重要な業務処理であればテストを追加する。

単純な表示やプラットフォーム依存処理など、リスクが低い場合は必ずしもテストを追加しない。

---

### 優先順位5：通常 UI コンポーネント

中核処理のテストが十分になった後で、一般的なUIコンポーネントの Coverage を補完する。

---

## 7. テストケース作成時の基本観点

重要な処理については、可能な範囲で以下を確認する。

### 正常系

- データ取得成功
- 作成成功
- 更新成功
- 削除成功
- 保存成功
- 確定成功

### 異常系

- APIエラー
- タイムアウト
- 無効なレスポンス
- 必須データ不足

### キャンセル

- 削除確認でキャンセル
- 未保存離脱でキャンセル
- キャンセル時にAPIが呼ばれないこと

### 権限制御

- VIEW
- EDIT
- OWNER

それぞれで表示・操作可能範囲が正しいことを確認する。

### 境界値

- 0
- 空配列
- 最大値・最小値
- 同点
- データなし
- 一部データ欠損

### 画面遷移

- 通常遷移
- Deep Link
- 削除後
- 戻る操作
- 履歴を残すべき場合
- 履歴を残すべきでない場合

---

## 8. Jest と Maestro の役割分担

Coverage を上げるために、Maestro で確認済みのシナリオをすべて Jest で重複してテストする必要はない。

### Jest

主に以下を担当する。

- 関数
- Hooks
- 条件分岐
- API成功・失敗
- エラー処理
- mutation
- router 呼び出し
- キャンセル時に処理されないこと
- 権限による表示・処理切替

### Maestro

主に以下を担当する。

- 実際のユーザー操作
- 複数画面をまたぐシナリオ
- Deep Link
- Android Back
- スワイプ
- 実機上の画面遷移
- APIとアプリを組み合わせたE2E
- Happy Path

重要な処理については、Jest で内部ロジックを固定し、Maestro でユーザー視点の動作を確認する。

---

## 9. Coverage 改善の終了条件

Coverage は100%を原則として目標にしない。

以下の状態になれば、そのファイルについては一旦十分と判断する。

1. ファイルの重要度に応じた目標値を概ね満たしている
2. 主要な正常系がテストされている
3. 重要な異常系がテストされている
4. キャンセルや権限制御など重要な Branch がテストされている
5. 主要なイベントハンドラや mutation が実行されている
6. 残っている未実行行が低リスクである

目標値を超えた後は、Coverage を1～2%上げるためだけのテスト追加は行わない。

Coverage が目標未達でも、残っているコードが以下の場合は許容できる。

- 自動生成コード
- 単純なラッパー
- プラットフォーム固有処理
- 到達困難な防御コード
- 業務上のリスクが非常に低い処理

その場合は、Coverage の数字ではなくリスクを基準に判断する。

---

## 10. 運用ルール

通常の開発では、機能追加や修正に対応する Jest テストを同時に追加する。

定期的に以下を実行して Coverage を確認する。

```bash
npm test -- --coverage
```

または、

```bash
npx jest --coverage
```

Coverage レポートを確認した際は、単純に Coverage が低い順にテストを作るのではなく、

1. 機能の重要度
2. Branch Coverage
3. Functions Coverage
4. 未実行行の処理内容
5. Lines / Statements Coverage

の順で判断する。

Coverage の生成物である以下のディレクトリは Git 管理対象外とする。

```text
coverage/
```

`.gitignore` に以下を登録する。

```gitignore
coverage/
```

---

## 11. 基本方針まとめ

Jest Coverage の運用では、以下を基本原則とする。

> **Coverage の数字を上げることではなく、壊れたときに影響の大きい処理をテストで守ることを目的とする。**

そのため、

- 重要コードは高い Coverage を求める
- 通常UIは必要以上に高い Coverage を求めない
- Branch と Functions を重視する
- 自動生成コードは対象外とする
- Jest と Maestro を適切に役割分担する
- 100% Coverage は目指さない
- Coverage 目標達成後は、数値よりリスクを基準に判断する

という方針で運用する。
