4. 未確定事項を推測で決めず、「実装前確認事項」として報告する。
5. ユーザーの承認後、後述の実装順序に沿って小さな単位で実装する。

## 2. 目的

- 下部ナビゲーションから、主要な移動操作と保存ページ一覧へ常時アクセスできるようにする。
- 大会ページ・卓ページを端末内に保存し、後から直接開けるようにする。
- 外部リンクやDeep Linkから子ページへ直接入ったユーザーに、そのページを保存する手段を提供する。
- ページタイトル長押しでも、明示的にページを保存できるようにする。
- 親ページのキーを知らない状態で子ページを開く現在の権限制約を崩さない。
- 複数の保存更新が同時に発生しても、保存済みデータを失わないようにする。

## 4. 前提と制約

1. 保存先はスマートフォン端末内とする。
2. 保存対象は大会と卓のみとする。
3. 子ページから親ページへアクセスできる権限を新たに付与しない。
4. 卓ページ取得時に親の大会名・グループ名を表示用に取得してもよいが、親ページへ遷移可能なキーをレスポンスや保存データへ不用意に追加しない。
5. 保存されたキーが無効、期限切れ、削除済み、またはアクセス不能になった場合でも、アプリをクラッシュさせない。
6. Storage更新はread-modify-writeの競合を起こさない実装にする。同一プロセス内の更新を直列化するなど、既存データ喪失を防ぐ。
7. API取得後に正式名称を得た場合は、保存済みの`name`を更新できるようにする。
8. 表示文言は既存のi18n方針に従い、コンポーネントへ日本語文字列を直接散在させない。

## 5. データモデル

```ts
type SavedLink = {
  type: 'tournament' | 'table';
  key: string;
  name: string;
  tournamentKey?: string;
  savedAt: string;
  lastOpenedAt: string;
};
```

### 5.1 各フィールド

- `type`: 保存対象の種類。`tournament`または`table`。
- `key`: 対象ページを開くためのキー。
- `name`: 一覧表示用名称。API取得後は取得した正式名称で更新する。
- `tournamentKey`: 卓に紐づく大会キーを保持できる任意項目。ただし、権限制約に反するキーを新たに取得・露出してはならない。現行画面が正当に保持している場合のみ設定する。
- `savedAt`: 初回保存日時。ISO 8601文字列。
- `lastOpenedAt`: 最終表示日時。ISO 8601文字列。

### 5.2 一意性

同一保存項目は、少なくとも`type + key`の組合せで一意に扱う。再保存では重複行を増やさず、既存項目を更新する。

### 5.3 日時更新

- 新規保存: `savedAt`と`lastOpenedAt`を現在時刻で設定する。
- 再保存: 原則として既存の`savedAt`を保持する。
- 保存済みページを開いた時: `lastOpenedAt`を更新する。
- APIから正式名称を取得した時: `name`を更新してよい。

## 6. ページ保存の判定

### 6.1 ダイレクト表示の判断基準

大会ページまたは卓ページを開いた際、画面が通常の親子ナビゲーションから受け取るはずの親ページキーがpropsまたはルート情報として渡されていない場合、その表示をダイレクト表示として扱う。

URLや履歴だけから推測せず、現行ルーティングで実際に受け渡している親キーの有無を基準にする。Expo Routerでprops以外の方法を使っている場合、同じ意味を持つルートパラメータまたはnavigation stateに読み替える。

### 6.2 保存案内モーダルの表示条件

次の条件をすべて満たす場合、`SavePagePromptModal`を表示する。

1. 対象が大会ページまたは卓ページである。
2. ダイレクト表示である。
3. 同じ`type + key`のSavedLinkが未保存である。
4. 対象ページのAPI取得が成功し、少なくとも保存に必要な`key`と`name`が確定している。
5. 同一表示中に、すでにモーダルを閉じていない。

### 6.3 表示しない条件

- 通常の親ページから遷移してきた。
- すでに保存済みである。
- API取得中または取得失敗中である。
- 当該画面表示中にユーザーがキャンセル済みである。
- 保存対象外ページである。

キャンセルは「今回の表示を続行する」ためのものであり、恒久的な非表示設定にはしない。次回、新たに同じ未保存ページをダイレクト表示した場合は再度案内してよい。

## 7. SavePagePromptModal

### 7.1 目的

Deep Linkなどから直接開いたページを、後で下部ナビゲーションから再訪できることを説明し、保存を促す。

### 7.2 必須内容

- 現在の大会または卓を保存できること。
- 保存すると下部ナビゲーションの保存ページ一覧から開けること。
- ページタイトルを長押ししても保存できること。
- 保存せずに続行できること。

### 7.3 操作

- `保存する`: SavedLinkへ保存し、モーダルを閉じる。
- `保存せず続行`: 保存せず、モーダルを閉じてページ利用を続行する。
- 閉じる操作が既存モーダル規約にある場合も、「保存せず続行」と同じ扱いにする。

保存成功・失敗時の通知は既存Toastおよび共通エラー方針に合わせる。保存失敗時に成功表示を出さない。

## 8. ページタイトル長押し

### 8.1 対象

- 大会ページのタイトル
- 卓ページのタイトル

### 8.2 挙動

- 未保存: 長押しで保存する。
- 保存済み: 重複追加せず、既存項目を維持または名称・最終表示日時を更新する。
- 通常タップ: 既存のタイトル動作を変更しない。
- 長押し可能であることは、モーダル内の説明でユーザーへ知らせる。

アクセシビリティのため、長押し以外にも保存操作へ到達できる導線を維持する。モーダルとSavedLinksPopoverがその代替導線となる。

## 9. 保存済みページ一覧

### 9.1 SavedLinksPopover

下部ナビゲーションの保存ページ項目から開く。少なくとも以下を提供する。

- 保存済み大会・卓の一覧表示
- 項目名と種類の識別
- 項目タップによる対象ページへの遷移
- 保存項目の削除
- 空状態表示

一覧は`lastOpenedAt`の降順で表示する。既存UI・過去仕様にこれと競合する並び順は確認されなかったため、仕様の第一候補を採用する。

### 9.2 項目を開く時

1. `type`に応じたルートを組み立てる。
2. 対象ページへ遷移する。
3. `lastOpenedAt`を更新する。
4. Popoverを閉じる。

無効な保存キーでAPI取得に失敗した場合は、共通エラーUIを表示する。自動削除するか、削除を促すかは既存エラー設計を確認して決定する。

## 10. BottomNavigation

### 10.1 役割

共通Layoutの下部へ設置し、現在画面から主要操作へアクセスできるようにする。保存ページ一覧の入口を必ず含める。

### 10.2 必須要件

- セーフエリアを考慮する。
- 画面本文や固定ボタンと重ならない。
- キーボード表示時の挙動を既存フォーム画面で確認する。
- アイコンだけに依存せず、`accessibilityLabel`を付与する。
- 現在位置または利用不能な操作は、既存デザインシステムに沿って状態表示する。
- 保存ページ項目から`SavedLinksPopover`を開ける。
- 共通Layoutへ一度組み込み、各ページで重複実装しない。

### 10.3 ナビゲーション項目

下部ナビゲーションは、現行のトップページ・設定ページと保存ページ一覧への入口から、以下の3項目とする。

- ホーム: `/` へ遷移する。
- 保存済み: `SavedLinksPopover` を開く。
- 設定: `/settings` へ遷移する。

戻る操作はこのナビゲーションに含めず、第11章の fallback 処理で扱う。

## 11. 戻る操作とfallback

Deep Linkや保存済みページから直接開いた場合、戻る履歴が存在しない可能性がある。

- 戻れる履歴がある場合: 通常の戻る処理を行う。
- 戻れる履歴がない場合: アプリの安全な既定ページへ遷移する。
- fallback先は現行ルート構成を調査して決める。既存のホームまたはトップページが第一候補。
- `push`で不必要な履歴を増やさず、必要に応じて`replace`を使う。
- Androidハードウェアバックと画面上の戻る操作で挙動が矛盾しないようにする。

## 12. HooksとStorage責務

### 12.1 SavedLink Storage

Storage層はUIやルーターに依存させず、少なくとも次の操作を提供する。

- 全件取得
- `type + key`による取得または存在確認
- 追加または更新（upsert）
- 削除
- `lastOpenedAt`更新
- 必要なら名称更新

公開関数名は既存命名規則へ合わせる。

### 12.2 同時更新対策

複数のread-modify-writeを並列実行すると、後勝ちで一部のSavedLinkが失われる。すべての変更操作を同じ直列化機構の内側で実行する。

要件:

- 追加、削除、名称更新、`lastOpenedAt`更新が同じ排他単位を共有する。
- 直列化の外側で古い全件配列を読み、その後書き戻す実装にしない。
- 1件の失敗後もキューが永久に停止しない。
- 同時に異なる2件を保存するテストで両方が残ることを確認する。
- 同じ項目を同時保存しても重複しないことを確認する。

### 12.3 useSavedLinks

保存済み一覧と一覧操作をUIへ提供する。想定責務:

- 保存済み一覧の購読・再取得
- 保存、削除、更新
- loading/error状態
- Storage変更後のUI同期

React Queryを使うかローカルstateを使うかは、現行のローカルStorage用hook方針へ合わせる。

### 12.4 useSavedPage

現在ページ単位の保存状態と操作を提供する。想定入力:

- `type`
- `key`
- `name`
- 必要な場合のみ`tournamentKey`
- ダイレクト表示判定に必要な親キー情報

想定出力:

- `isSaved`
- `save`
- `remove`または削除操作への接続
- `shouldPromptSave`
- モーダルを今回閉じた状態を管理する操作

Hook内部でページ固有APIを直接呼ばず、ページが取得済みデータを渡す構成を優先する。

## 15. テスト要件

### 15.1 Storage Unit Test

- 空状態の取得
- 新規保存
- 同一`type + key`の再保存で重複しない
- 大会と卓で同じ`key`文字列でも別項目として扱える
- 削除
- 名称更新
- `lastOpenedAt`更新
- 不正JSONまたはStorage読込失敗時の既存方針に沿った処理
- 異なる2件の同時保存で両方が残る
- 保存と削除の競合でもデータ破損しない
- 1操作失敗後も後続操作が実行できる

### 15.2 Hook Test

- 保存状態の初期取得
- 保存後に`isSaved`と一覧が更新される
- 削除後に一覧が更新される
- ダイレクト表示かつ未保存で`shouldPromptSave = true`
- 保存済み、通常遷移、API未確定ではpromptしない
- キャンセル後は同一画面表示中に再表示しない

### 15.3 Component Test

- SavePagePromptModalの説明と2つの主要操作
- 保存成功時にモーダルが閉じる
- 保存失敗時のエラー通知
- タイトル長押しで保存処理を呼ぶ
- 通常タップの既存挙動を壊さない
- SavedLinksPopoverの一覧、空状態、遷移、削除
- BottomNavigationからPopoverを開ける
- accessibilityLabelと操作可能状態

### 15.4 Deep Link結合テスト

- 未保存の大会Deep Link → データ取得成功 → 保存案内表示
- 未保存の卓Deep Link → データ取得成功 → 保存案内表示
- 保存する → 一覧に出る → 一覧から再度開ける
- 保存せず続行 → ページを利用できる
- 保存済みDeep Link → 案内を出さない
- API失敗 → 保存案内を出さず共通エラーを表示
- 履歴なしの戻る → fallback先へ移動
- 履歴ありの戻る → 直前画面へ戻る

## 17. 受入条件

- 大会・卓を保存でき、アプリ再起動後も保持される。
- 同じページを複数回保存しても重複しない。
- 同時更新でも他の保存項目が消えない。
- Deep Linkで未保存ページを開いた場合だけ、データ取得後に保存案内が出る。
- ユーザーは保存せず利用を続けられる。
- ページタイトル長押しで保存できる。
- 下部ナビゲーションから保存済みページ一覧を開ける。
- 保存済み一覧から大会・卓へ直接遷移できる。
- 履歴がない状態の戻る操作でも行き止まりやクラッシュが起きない。
- 既存の通常ナビゲーション、権限境界、タイトルの通常操作を壊さない。
- 必要なUnit / Hook / Component / Deep Linkテストが通る。

## 18. 実装前にCodexが確認して報告する事項

1. `SavedLink`型を置く既存の型ディレクトリと命名規則。
2. SecureStore、AsyncStorage、または既存`appStorage`のどれを使うべきか。
3. 既存Storageに直列化・mutex・更新キューがあるか。
4. 大会・卓ページの実ファイルパスとルートパラメータ。
5. 通常遷移時に渡される「親ページキー」の実体と、ダイレクト表示判定方法。
6. ページタイトル共通コンポーネントが`onLongPress`を受け取れるか。
7. 共通Layoutの実ファイルと、固定UI・SafeArea・キーボードへの影響。
8. 既存Popover / Modal / Toast / Icon部品の流用可否。
9. 戻る可否を判定する既存APIとfallback先。
10. 下部ナビゲーションのボタン構成、名称、アイコンについて過去仕様を裏付ける既存コードまたは資料があるか。
11. 保存一覧の並び順と、無効キーを自動削除するか確認を求めるか。
12. Jest / React Native Testing Library / Maestroの既存構成と追加先。
